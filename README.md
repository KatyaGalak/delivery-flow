# Delivery Flow (микросервисный backend для сервиса доставки еды)

## Задачи системы
Клиент оформляет заказ, далее система должна:
1. сохранить заказ
2. провести оплату
3. отправить заказ на выполнение на кухню
4. передать готовый заказ курьеру
5. зафиксировать успешное завершение заказа или его отмену

## Стек
- **Java 21**
- **Spring Boot 3.3** - фреймворк для сервисов
- **Spring Security + JWT** - авторизация и аутентификация
- **Apache Kafka** - асинхронная коммуникация между сервисами
- **Camunda 7** - оркестрация бизнес-процессов
- **PostgreSQL** - отдельная база данных для каждого сервиса
- **Docker Compose** - контейнеризация инфраструктурных сервисов (PostgreSQL, Kafka, Zookeeper)
- **Gradle** - сборка проекта и управление зависимостями
- **Insomnia** - тестирование API

## Состав системы

1) api-gateway (порт 8081)

   Точка входа для клиента
   - регистрирует пользователей (username, password, имя, email, роль)
   - выполняет вход и выдаёт JWT
   - принимает создание заказа (POST /api/orders) и получение заказа по id
   - при создании заказа:
   получает текущего пользователя из SecurityContext (по JWT)
   формирует сообщение с correlation ID
   отправляет его в Kafka (create-order-requests)
   ждёт ответ в create-order-responses (до 5 сек)
   возвращает клиенту результат или ошибку

    Не работает напрямую с заказами, не содержит логику про оплату и доставку. Хранит только пользователей


2) order-service (порт 8082)

Работа с заказами

- слушает create-order-requests
- создаёт заказ в своей БД (userId, restaurantId, адрес, позиции, сумма, статус CREATED)
- считает общую сумму по позициям
- отвечает gateway через create-order-responses
- публикует событие order-created (orderId, userId, totalAmount, ...);
- отдаёт заказ по id (get-order request/response)

Не производит оплату, не назначает курьера

3) payment-service (порт 8083)

Обработка платежей

- слушает process-payment-requests
- имитирует эквайринг (задержка 1.5 секунды)
- с вероятностью 95% считает оплату успешной
- payment-completed - успех
- payment-failed - отказ оплаты

Не общается с клиентом, не управляет процессом доставки

4) kitchen-delivery-service (порт 8084)

Оркестратор жизненного цикла заказа (Camunda 7)

- слушает order-created и начинает BPMN-процесс
- отправляет команду на оплату заказа (process-payment-requests) через JavaDelegate. Далее ждёт сообщение:

  - PaymentReceivedMessage (payment-completed)
  - PaymentFailedMessage (payment-failed)

- при успехе оплаты:
  - Task Prepare Food (группа ROLE_RESTAURANT)
  - Task «Deliver Food» (группа ROLE_COURIER)

- при ошибке оплаты происходит завершение процесса выполнения заказа
- выдаёт список задач по группе (для кухни и курьеров)
- в случае, если процесс происходит слишком долго (для демонстрации таймер на одну минуту), заказ отменяется и пользователю возвращаются деньги
- выполнение complete задачи по её Id (завершение приготовления и доставки)
- UI Camunda: Cockpit / Tasklist

Необходим для выполнения сценария "запрос оплаты → ожидание результата → задачи ресторану и курьеру -> завершение заказа"

## Инфраструктура
- отдельные PostgreSQL для каждого сервиса - данные изолированы
- Camunda 7 - BPMN-процесс DeliveryProcess

## Основные API

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/orders (с токеном)`
- `GET /api/orders/{id}`
